# 도구 선택 평가 게이트 (N055 6장)

코드나 지시문을 바꾼 PR 이 도구 선택을 망가뜨리지 않았는지, **머지 전에** 실제 LLM 으로 확인하는 문이다.

## 언제 도나
- PR 에 `eval` 라벨을 붙이면(같은 저장소의 PR 만), 또는 Actions > eval > Run workflow 버튼을 누르면 돈다. PR 마다 자동으로 돌지 않는다(41개 x 2회 = 약 80번 LLM 호출).
- 시크릿 `LLM_API_KEY` 가 필요하다. Langfuse 키는 쓰지 않는다. 코드의 지시문(`app/router.py`, Langfuse production 버전 3과 같은 문장)으로 평가한다.

## 무엇을 재나
`python scripts/eval_tools.py --full --repeat 2 --min-exact 33 --must-pass T34`
- `--full`: 서비스가 실제로 거치는 `choose()` 전체(코드 안전장치 포함)로 평가한다. 모델 선택만 보면 안전장치가 만든 오류(예: N054 의 날짜 안전장치가 "시험 전날"을 시험 당일로 덮어쓴 일)를 놓친다.
- 두 회차 모두 "도구와 인자 모두 정답"이 33개 이상이어야 하고, T34(시험 전날 날짜 계산)는 두 회차 모두 정답이어야 한다. 아니면 종료 코드 1로 실패한다.

## 기준을 어떻게 정했나 (2026-11-03)
같은 모델(gpt-4o-mini), 같은 지시문(버전 3), `--full`로 7번 돌린 "도구와 인자 모두 정답" 수: **38, 36, 35, 38, 39, 38, 39** (최솟값 35, 최댓값 39).
- LLM 응답은 실행마다 조금씩 달라 같은 코드로도 3~4개가 오르내린다. 그래서 **관측 최솟값에서 2를 뺀 33**을 기준으로 했다.
- T16(날씨 하소연에 도구를 고름)·T33(알림 시각 08:00 대 09:00)은 항상 틀리는 기존 실패라 41개 전부를 요구하지 않는다.
- T34는 코드(`when.parse_when`)가 날짜를 정하므로 모델이 틀려도 맞다. 7번 중 이 수정 뒤 5번 연속 정답이었다(수정 전 두 번 모두 오답).
- 한계: 이 게이트는 **큰 후퇴**(기준보다 3개 이상 줄거나 T34가 깨지는 것)를 잡는다. 한두 개의 미세한 후퇴는 흔들림과 구별되지 않아 못 잡는다. 그런 것은 데이터셋 실험(Langfuse Experiments)에서 항목별로 본다.

## 기준을 바꿀 때
지시문이나 평가 데이터를 크게 바꿨으면 로컬에서 `--full --repeat 3`을 몇 번 돌려 새 최솟값을 보고 이 표와 `.github/workflows/eval.yml` 의 숫자를 함께 고친다(`tests/test_workflows.py` 가 숫자가 있는지 확인한다).
